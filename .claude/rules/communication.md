# Communication Rules

## Options & Recommendations
- When presenting options, ALWAYS use a table format with emoji indicators.
- Always provide a recommended approach. If options are equivalent, say so explicitly.
- Format:

| | Option | Pros | Cons |
|---|---|---|---|
| ⭐ | **Recommended option** | Why it wins | Tradeoffs |
| 🔄 | Alternative A | Strengths | Weaknesses |
| 🔧 | Alternative B | Strengths | Weaknesses |

- If options are equivalent:
> These approaches are equivalent in practice. Pick based on team preference.

## After Task Completion
- After finishing ANY task, always provide:

### ✨ QoL / Polish (3-5 suggestions)
Quick improvements that would enhance what was just built.

### 🔜 Follow-up Tasks (2-3 suggestions)
Natural next steps that build on the completed work.

## General Communication
- Be concise. Lead with the answer, then explain.
- Use code blocks with language tags for all code.
- Reference files as `path/to/file.ts:lineNumber` when discussing specific code.
- When explaining trade-offs, use tables. When listing steps, use numbered lists.
- Do not add emojis unless this rule explicitly uses them or the user requests them.
